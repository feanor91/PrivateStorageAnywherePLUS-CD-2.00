# Port to Crimson Desert build 3663 (19 November 2026 update)

3527 was the last build confirmed in game ([PORT-3527.md](PORT-3527.md)). 3663
stopped the build twice, on two unrelated things. Procedure in
[PORTING.md](PORTING.md).

## Stop 1: the tag-name pool grew past its window

```
STOP: the gameplay sub-mode ('interaction') is not unique: []
jump table game+0x731af4 (18 entries): [2]=fadeout [3]=fadeout [4]=cinema
    [5]=store [6]=hud-info [11]=gimmick [15]=hud-info [16]=hud-info [17]=hud-info
```

Read the table against 3460's
(`[4]=cinema/subtitle ... [17]=hud-info/hud-play/interaction`): same 18
entries, but `subtitle`, `hud-play` and `interaction` had vanished from every
entry. Nothing had changed in the code that emits them; the *lookup* of the
names had. `find_tag_pool` finds `ingame-global` and looks for the other ten
tag strings within +-0x200 bytes of it. Measured on 3663:

```
hud-info       -0x10     global       -0x40     ingame-global  +0x0
store          +0x1ac    fadeout      +0x1b8    cinema         +0x1c0   gimmick   +0x1c8
interaction    +0x238    hud-play     +0x248    subtitle       +0x258   quickslot +0x268
```

Four names now sit past +0x200, so they were never mapped to an address and
`tags_emitted` silently dropped them. **The failure mode matters**: nothing
reported a missing tag, the table simply came out with fewer labels, and the
build died three steps later on a consequence (`'interaction' is not unique:
[]`) rather than on the cause.

Fix (`tools/derive_modestate.py`): the window is +-0x800, and a name that occurs
twice inside it now stops the build instead of picking one. Each tag is a whole
NUL-delimited string and occurs exactly once in the image (checked on 3663), so
widening cannot mis-attribute. With it the table reads exactly as on 3460 and
every derived layout value is unchanged.

## Stop 2: the manager globals are gone

```
STOP: too few manager globals found (0)
```

`derive_manager_window` located the block of StaticInfoManager globals by the
bucket idiom `shl r11,8 ; add r11,[r10+0x78]` with `mov r10,[rip+G]` in the
0x60 bytes before it: 91 distinct globals on 3527. On 3663 the exact idiom
occurs **once**, and for a structural reason, not a register-allocation one:

```
2bf4d15  mov rdi, rcx              <- the manager arrives as `this`
2bf4d4a  cmp dword [rdi+0x6c], r13d
2bf4d54  mov ecx, dword [rdi+0x68]
2bf4d5d  mov eax, r8d ; div ecx    <- hash % bucket count
2bf4d65  shl r10, 8
2bf4d69  add r10, [rdi+0x78]       <- bucket array
```

The bucket walk has been **outlined into member functions**, one per
StaticInfoManager type. Measured:

| | |
|---|---|
| same shape, any base register, same register shifted and added, no SIB | 67 sites in 59 functions |
| of those, with a `mov M,[rip+G]` in the 0x60 bytes before | **0** |
| direct calls into those 59 functions | 223 |
| ...with a `mov rcx,[rip+G]` in the 0x40 bytes before | 13 (4 distinct globals) |
| ...traced from `mov rcx,R` back to a global load anywhere in the function | 7 (3 distinct globals) |

The callers receive the manager from other objects, not from a global they
load themselves, so the cluster cannot be reconstructed from call sites on this
build. The route is closed, not merely moved.

### What the window is for, and the fallback

The window is a **speed bound**, not part of the identification. INVSCAN walks
it qword by qword and accepts a pointer only if the object it points to carries
the vptr of `pa::InventoryInfoManager`, derived from the executable's RTTI
(`game+0x5ce98e0` here). Every candidate is `VirtualQuery`-checked before it is
read. A wider window can only cost time, never accept a wrong object.

So when no cluster can be derived the window falls back to **the whole data
section that holds the mainChar global**, derived from the image, not typed:

```
manager globals: only 0 found (the bucket walk is outlined on this build);
window = the whole data section holding mainChar (.sxdata)
manager scan window game+0x6d56000..0x75c7000 (1106432 qwords)
```

Section names are randomised per build (`.sxdata` here, `.data` on 3527), which
is why it is found by containing the global rather than by name. The reason to
expect the manager in the same section is circumstantial: it was at
mainChar+0xF08 on 3460, 3479 and 3527, and the cluster began at mainChar+0xEC8
on 3479 and 3527. On 3663 mainChar+0xF08 (`game+0x7246120`) has **no code
reference at all**, which is consistent with the manager no longer being
reached through a global but does not prove it still lives in one.

Cost, as built: the loop rejects a qword by value (<= 0x10000), alignment or
canonical form before anything else, so only plausible heap pointers reach
`VirtualQuery`. The old window was 32768 qwords; this one is 1106432. It stops
at the first exact match, and the retry bound (`INV_MAX_TRIES`, one attempt per
second of the worker) is unchanged, so the failure case is bounded too. The
cluster route is tried first, so builds where it works are byte-for-byte
unchanged.

## Status

`CD 3663.BB` (`ccc8fbd4...`) built and **installed** by `MAJ-mod.ps1`; the
previous build (3527, the last confirmed in game) is kept in `bin64` as
`PrivateStorageAnywhere.asi.avant-3663.bak`. **Not yet confirmed in game.**

What the log must show, in this order, for the chests to work:

```
HOOK CanShow: OK slot base+0x... -> detour (orig +0x...)
  [INV] InventoryInfoManager global at base+0x... (object ..., vtable match) - housing slot patch enabled
  [DBG] slot patcher -> N              (N = 8 on 3460..3527)
InventoryInfo slot patch: N entries default 10 -> 1000
```

Three things here are **unverified on 3663** and the build cannot check them
statically:

1. that the manager's global is still inside the section scanned. If not,
   there is no `[INV]` line (or `giveup`), and F5-F9 open but stay at 10;
2. that the entry capacity pair is still at `+0x10/+0x14`. If not,
   `[DBG] slot patcher -> 0` and `[PRIV] no entry: stage N` (numbered refusals,
   see PORTING.md section 0);
3. that `CAMP_KEY = 8` still names the private warehouse (stage 6 or 7).

The panels themselves (F4-F9 opening) depend on none of them.
