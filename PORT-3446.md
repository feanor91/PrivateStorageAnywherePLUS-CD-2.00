# Port to Crimson Desert build 3446 (30 October 2026 update)

The first update that made the game **crash on launch** with the mod
installed, rather than merely stop working. Procedure in [PORTING.md](PORTING.md).

The installed build was `CD 2976.BC`. Its log reaches `READY!` and stops.

## The crash: the CanShow hook guessed a prologue length

The upstream installer asks `FindPrologBoundary` for an instruction boundary
at or past 14 bytes and, when that fails, logs

```
  FindPrologBoundary: unknown opcode 0x74 at pos 10
HOOK CanShow: prolog boundary not detected (got 0), falling back to fixed 14 bytes
HOOK CanShow: OK base+0xA277270 (size=14)
```

and hooks anyway. On 3446 that function begins:

```
+0   mov rax,[rcx+8]            (4)
+4   mov r9,rcx                 (3)
+7   test rax,rax               (3)
+10  je rel8                    (2)   <- relative branch inside the stolen bytes
+12  movzx r8d,word [rax+0x8a]  (8)   <- the 14-byte cut splits this instruction
```

Fourteen bytes therefore (a) end mid-instruction, so the trampoline's tail is
garbage, and (b) relocate a `je rel8` whose target is computed from the
original address. Either is fatal, and CanShow runs immediately. The other two
hooks take 15 bytes and land on clean boundaries, which is why only this one
breaks.

**First fix (keeps the game alive):** `mov esi,0xE` at ASI `0x601E` is five
bytes, exactly a `jmp rel32`, so the guess now jumps to the installer's own
ABORT path at `0x61B3`. Applied to every build: guessing a prologue length is
unsafe on any version, and where the boundary is found the patch changes
nothing.

That stopped the crash but cost the panels. The installer's caller treats a
failed CanShow hook as fatal (`7D43 test al,al ; 7D45 je <give up>`), so the
mod never reached `READY!`. Removing that branch got `READY!` back, and then
every hotkey did this:

```
=== OPENING WAREHOUSE (Private) ===
  ViewMount: state set (current=1, request=1)
  Warehouse opened (mode=0x04 sub=0x11)
<nothing further>
```

compared with a working build, where the next lines are

```
  Warehouse opened (mode=0x04 sub=0x10)
AUTO-CAPTURED warehouse controller: 0x2BFEB37F000 (panelId=0x0000)
  Warehouse opened (mode=0x04 sub=0x05)
  ...
  InitWarehousePanel done state: ...
```

The HUD hid and the sub-mode never moved to 5 (`store`), because the detour is
precisely what lets a warehouse open away from its chest. **CanShow is not
optional.**

## Real fix: hook the vtable slot, not the prologue

AX patches CanShow's first bytes with `jmp [rip+0]` plus an 8-byte address --
14 bytes, because the ASI and the game module are far further apart than a
`rel32` reaches. 3446 offers ten. No amount of care makes fourteen fit.

But the prologue is not the only way in. The mod already *finds* CanShow by
reading it out of `UIGamePlayControlRootWarehouse2`'s vtable, and that slot is
ordinary data: point it at the detour and the game arrives there by itself,
with CanShow's code untouched. The detour reaches the original through a
single pointer (`0x40950`, which the prologue installer fills with its
trampoline); aiming that straight at CanShow gives it exactly what it expects.

Three edits, all at AX-fixed rvas verified by `expect`:

| rva | was | now |
|---|---|---|
| `0x9965` | `mov [VT_PTR],rdi` on the resolver's hit path | `jmp` to a stub that does that store, **keeps `rsi`** (the slot address, live there but never recorded) in `.psdata+72`, and rejoins at `0x996C` |
| `0x7D3E` | `call` the prologue installer | `call` the stub below |
| `0x601E` | `mov esi,0xE` (the guess) | `jmp` ABORT |

and one stub in the free tail of `.pstext`:

```
HOOK(rcx = CanShow) -> al
    slot = [.psdata+72]
    if slot == 0 or [slot] != rcx:  tail-call AX's prologue installer   ; WRONG, see PORT-3460.md
    VirtualProtect(slot, 8, PAGE_READWRITE, &old)
    [0x40950] = rcx                 ; the detour's "call the original"
    [slot]    = &detour (0xC0B0)
    VirtualProtect(slot, 8, old, &old)
    log "HOOK CanShow: OK vtable slot base+0x%llX -> detour (orig base+0x%llX)"
    return 1
```

The fallback matters: on a build where the slot is not recorded, or already
holds something else, the old prologue route is still tried. Failure stays
fatal, as AX had it -- without this detour nothing opens, so a loud `ABORT`
beats a `READY!` that does nothing.

This also means the prologue shape of CanShow no longer matters on any future
build.

## Then: the gameplay sub-mode moved

```
HOTKEY Private (vk=0x73) -> OPEN
  [MODE] c1 ptr=2BACCFE1540 m=04 s=11 f=00 t=00 d=01 x=0000
BLOCKED: unsafe state (mode=0x04 sub=0x11)
```

The safe-state gate accepts the gameplay sub-modes as a range starting at 15:

```
B4DF  lea eax,[rcx-0xf]
B4E2  cmp al,1            -> cmp al,2
B4E4  ja  <BLOCKED>
```

i.e. `{15,16}` as built for 2.00. The eighteenth sub-mode pushed the full
gameplay HUD from 16 to 17. The span is now derived from the jump table: the
one entry that emits `interaction` is the top of the range.

## Along the way: the sub-mode count is not fixed

The build also stopped on

```
STOP: layout invariant failed: dirty == subtypes + 0x23
      ({'mode': 48, 'submode': 50, 'flags': 58, 'subtypes': 65, 'dirty': 102})
```

The sub-mode jump table grew from 17 to 18 entries. `subtypes[n]` is followed
by its shadow copy and then `dirty`, so the gap is `2*n + 1`: `0x23` for 17,
`0x25` for 18. The invariant now derives `n` from the sub-mode table instead of
hardcoding the gap, and the two tables are told apart by which one emits
`ingame-global` rather than by their size (both carry a `store` entry).

Every earlier build satisfies the general form: 2850 `0x38 + 35 = 0x5B`,
2944/2976 `0x39 + 35 = 0x5C`, 3446 `0x41 + 37 = 0x66`.

## Status

`CD 3446.BB` (`20536688...`, full build) is installed. `CD 3446.AY`
(`950a828f...`, panels only) sits in `patched/` as the fallback.

Tested in game across four rounds on this build: the crash, the missing
`READY!`, the `BLOCKED` gate and the silent panels each came from one of the
four changes above.

**The vtable hook never installed.** Its guard compared the slot's contents
against the address the resolver reported, and on this family of builds the
slot holds a `jmp` thunk to that address, not the address — so the guard
rejected a slot that was perfectly good. Fixed on the next build; see
[PORT-3460.md](PORT-3460.md), which also supersedes the stub listed above.
The game updated to 3460 before this one could be tested again.
