# Port to Crimson Desert build 3732 (19 November 2026, second update of the day)

The game updated again while 3663 (see [PORT-3663.md](PORT-3663.md)) was waiting
to be tested, so **3663 was never tested in game**. The user re-ran
`MAJ-mod.bat` on 3732 and the game stopped launching.

## What the log says

[docs/logs-3732/log-3732-BB-CRASH-slotpatcher-minus1.txt](docs/logs-3732/log-3732-BB-CRASH-slotpatcher-minus1.txt)

```
HOOK CanShow: OK slot base+0x5A759A8 -> detour (orig +0xF20130)
=== READY! Press F6 to open Private Storage from anywhere ===
  [INV] InventoryInfoManager global at base+0x724C4F0 (object 31F8212DF80, vtable match) - housing slot patch enabled
  [DBG] slot patcher -> -1
<end of log>
```

Three facts, in order of how much they settle:

1. **The whole-section fallback from 3663 worked.** The manager's global was
   found by the exact RTTI vtable test, in the section scanned
   (mainChar global `game+0x724B3A8`, manager global `game+0x724C4F0`: **+0x1148**,
   not the +0xF08 it had on 3460/3479/3527). The window assumption held, the
   offset assumption would not have.
2. **Everything before that is fine on 3732**: the 18-entry sub-mode table
   reads exactly as on 3460 (`[17]=hud-info/hud-play/interaction`), the layout
   is unchanged, the CanShow vtable hook installed on the first try.
3. **The slot patcher returned -1.** In the AX code `-1` is the value its SEH
   handler returns: the walk over the manager's entries took an access
   violation and was caught. On 3460..3527 it returned 8. So the manager's
   *internal* layout (`[mgr+0x58]` entry array, `[mgr+8]` count, the entry
   stride, the capacity pair at `+0x10/+0x14`) no longer matches the AX walk.

The log stops there and never prints the `[PRIV] exp=... base 240 -> 900` line
that follows the patcher on every working build. That line comes from the
boot-time apply, which walks the same structure *outside* the patcher's SEH
frame, so the likeliest reading is that it dereferenced the wrong layout and
took the game down at load. This is inference from the log's last line, not
something observed: no crash dump was read.

## What was done

- The mod was moved aside (`PrivateStorageAnywhere.asi.DESACTIVE`) so the game
  can start; a copy of the build that crashed is kept as
  `PrivateStorageAnywhere.asi.3732-PLANTE.bak` in `bin64`.
- A **panels-only** build for 3732 was made (`CD 3732.AY`, `b0041b9b...`): same
  derivations, CanShow hook, safe-state gate, but the slot patcher call returns
  0 and the private-warehouse wrapper exits before any game lookup, so nothing
  reads or writes inventory data. It is **not installed**; `MAJ-mod-prudent.bat`
  installs it (`MAJ-mod.ps1 -SansAgrandissement`).

## Not yet known

- Whether the game starts at all without the mod on 3732 (the user is checking).
  If it does not, the cause is not the mod.
- Whether `CD 3732.AY` opens the panels. Its ingredients all worked in the log
  above, but it has not run.
- Where the manager's internal layout moved. Needs a dump of the manager and
  its entries (`--dump-mgr`, see PORT-3460.md) on a build that does not crash
  first, i.e. the dump itself must be made crash-proof (it already guards every
  dereference with `rdbl`).

The five housing chests stay at their native size and the private warehouse is

## Diagnostic build DX: where did the manager's layout go?

`MAJ-mod-diagnostic.bat` (= `MAJ-mod.ps1 -Diagnostic` = `retarget_ay.py
--housing --dump-mgr`, tag `CD 3732.DX`, `c0f46478...`). Built, **not
installed** (the AY build that works stays in place until the user runs it).

What it is designed not to do, because 3732's BB build died right after
`slot patcher -> -1`:

- the private-storage walk stays closed behind AY's capacity gate (`90 e9 ...`
  at `0x461a2`, checked in the output);
- the slot patcher is **not run**: its call site is retargeted to a stub that
  dumps the manager once and returns 0;
- the dump block (111 instructions, disassembled) has **no store outside
  `.psdata`**, and its only calls are the dump routine, `rdbl`, and the logger;
- every read, including each qword of the manager and of each entry, goes
  through `rdbl` (VirtualQuery-backed), so a wrong guess logs less, not a crash.

`BB` and `AY` rebuilt from the same script are byte-identical to before
(`7a9e7cea...`, `b0041b9b...`), so the change touches nothing outside `--dump-mgr`.

What it logs, once, after the manager is found:

```
[DBG] mgr+08 count=N  mgr+58 array=...        <- what the walk would have been given
[DBG] mgr+00 = ...  ... mgr+170 = ...          <- the manager's first 48 qwords
[DBG] entry[j] = <pointer>                     <- j < min(count, 0x40)
[DBG]   entry[j] +00 = ...  ... +78 = ...      <- sixteen qwords per entry
```

Differences from the 3460 dump: the entry count comes from `[mgr+8]` instead of
a fixed 24, an entry is sixteen qwords (0x80) instead of fourteen, and the
count line is new. Reading it: the chests show **10** (or 0x000A) at the
capacity word and the private warehouse **240** with **1000** as its max, as on
3460 (`+0x10` / `+0x14` there). Look for entries whose key (dword at `+8` there)
runs 1..N, and for the same pair at a new offset; if the count is larger than
the 24 the AX patcher assumed, or an entry pointer is null, that alone could
explain an exception in an unguarded loop without any layout change.

## What the first DX log showed (the manager was re-laid out)

[docs/logs-3732/log-3732-DX-manager-dump.txt](docs/logs-3732/log-3732-DX-manager-dump.txt).
The manager was found (vptr match, `game+0x724C4F0`), and read with the AX
offsets it is nonsense:

```
mgr+08 count=748780384  mgr+58 array=0000001800000018     <- not a count, not a pointer
mgr+00 = 0000000145CEECA8       the vtable (game+0x5CEECA8)  correct
mgr+50 = 0000001800000001       dwords 1, 24
mgr+54..                        (the 24 = entry count)
mgr+60 = 0000040B6E31E600       a pointer: the bucket array
mgr+68 = 0000040B6E238B80       a pointer: the entry-pointer array
mgr+78 = 0003000200010000 ...   24 uint16 (0..23, shuffled): not a pointer
```

That is the whole crash. AX reads `[mgr+0x78]` as the bucket array; on 3732 it
holds `0x0003000200010000`. The private-storage walk dereferences it outside any
SEH frame, which is why the log of the BB build ended right after the patcher's
`-1` and the game died. (The patcher is SEH-wrapped and only returned -1.)

### What the game reads instead (static, from its own code)

Functions that load the manager's global and walk its buckets
(`game+0x2A52B70`, `game+0x89278F0`, ...) read, on 3732:

```
cmp  dword [M+0x54], 0        entry count          (AX: +0x6C, and +0x08)
mov  ecx, dword [M+0x50]      bucket count (div)   (AX: +0x68)
add  r, qword [M+0x60]        bucket array         (AX: +0x78)
mov  rcx, qword [M+0x68]      entry-pointer array  (AX: +0x58)
cmp  word [entry+4], key      the entry carries its key as a word at +4
```

The bucket layout inside (`[bucket] = count`, `[bucket+i*8+8] = key`,
`[bucket+i*8+0xC] = index`, 0x100 bytes per bucket) is unchanged, so the AX
walk's logic is still right and only the five displacements move. `PORT-3663.md`
is wrong about why the cluster disappeared; see its correction.

### How it is derived, not typed

`derive_manager_layout` finds every `shl R,8 ; add R,[M+Z]` (any registers, any
`Z`), groups them by `Z`, and takes the group whose sites load the most
distinct globals right before. Measured on 3732:

| bucket disp `Z` | sites | distinct globals loaded |
|---|---|---|
| **0x60** | 2184 | **127** |
| 0x10 | 1028 | 28 |
| 0x28 | 678 | 2 |
| 0x78 (the old layout) | 66 | 0 |

It must beat the runner-up two to one or the build stops, and it takes `div`,
`count` and `entries` by majority over up to 80 of that group's sites (each must
agree for 80%). Result: `+0x50 / +0x54 / +0x60 / +0x68`, exactly what was read
by hand. The window it also yields (`game+0x723C000..0x727C000`, 32768 qwords)
contains the manager's global, so the 1.1-million-qword fallback is no longer
needed here (it stays as the last resort).

The eight reads in AX's code (`MGR_SITES`: five in the private-storage walk,
two in the slot patcher) are `disp8`, and so are the new values, so each patch
is one byte. When the derived bucket displacement is AX's own 0x78 nothing is
touched.

### Still unknown: the entries themselves

The entries (`[array + index*8]`) are separate objects whose layout is not
visible from the manager. On 3460 the capacity pair moved from `+0x48/+0x4A` to
`+0x10/+0x14`; on 3732 the entry's key is a word at `+4` where AX had a dword at
`+8`, so the struct was re-laid out again and the capacity pair is somewhere
else. The first DX could not show it (it indexed with the old `+0x58`). The
second DX (this commit) uses the derived offsets, takes the count from the
manager and dumps **thirty-two qwords per entry**.

Reading it: one entry has the pair 240 / 1000 (the private warehouse, key 8),
the five chests have 10 / 1000, and the ones that cannot be extended repeat one
value twice (300/300, 50/50, 5/5), as on 3460. Do not touch `ENTRY_BASE` /
`ENTRY_MAX` until the dump says where they are.

## The second DX log: the "entries" are not the objects

[docs/logs-3732/log-3732-DX2-records.txt](docs/logs-3732/log-3732-DX2-records.txt).
With the derived offsets the dump finally read a sane count (`entry count=24`)
and an array, and the 24 "entries" it printed were **8 bytes apart**:

```
entry[0] = ...6A6E9F0    entry[1] = ...6A6E9F8    entry[2] = ...6A6EA00   ...
entry[0] +00 = 0000000100000000     entry[1] +00 = 0001000200000001
```

Overlapping windows over one packed stream: each record is 8 bytes,
`{ u32 j ; u16 key ; u16 j }` with `key = j + 1` (the game's own lookup compares
`word [record+4]` with the key). So `[mgr+0x68]` is the bucket walk's validation
array, **not** the InventoryInfo objects. Nothing like a capacity word is in it.
That is also why the AX F4 walk cannot be fixed by changing one displacement:
it would read `word [record+0x10]` from the middle of the stream and, live,
write through it.

### Where the objects are

The game's own getter, `game+0x57B750`, is the only small function that loads
the manager's global and reads both `[mgr+0x28]` and `[mgr+0x20]`:

```
cmp  r8d, [mgr+0x28]            id < count
mov  rax, [mgr+0x20]            table of 0x18-byte elements
lea  rdx, [r8+r8*2]
cmp  qword [rax+rdx*8+8], 0     the object pointer; null until loaded
```

The first DX's raw manager already showed it: `mgr+20` a heap pointer, `mgr+28` =
`24 | 32<<32` (count, then capacity). It has 248 callers; on the object it
returns they read a **word at +0x10** (9 sites) and a **word at +0x14** (13
sites) - the pair AX edits, as on 3460 - and a word at `+8` (73 sites, the key).

### What the build does with that

For a non-AX layout, `apply_manager_offsets` (a) points the slot patcher's table
and count at `+0x20` / `+0x28` (`INFO_TABLE`, measured, not derived), (b)
rewrites its element addressing from `[array + j*8]` to
`[table + j*0x18 + 8]` (`lea eax,[rdx+rdx*2] ; mov rax,[r10+rax*8+8]`, in place,
three nops), and (c) routes the write through a guard (`apply_chest_guard`):

```
inline (unchanged, inside the patcher's __try):  cmp word [rax+0x10],10 ; jne skip
stub in the gap (outside it):  cmp word [rax+0x14],1000 ; jne skip
                               mov word [rax+0x10],r11w     <- AX's write
                               jmp  inc r8d
```

so a chest is raised only if it carries **both** `10` at `+0x10` and `1000` at
`+0x14`. A wrong layout costs the feature, never data. The first read stays
inline on purpose: the patcher's `__try/__except` covers only its own addresses
(that is what produced `-1` on 3732), so a fault in the stub would be unhandled;
the stub only reads the next word of a page it has just read.

**F4 is not built** when the layout is not AX's: `--f4` degrades to the AZ build
with a note in the build log. The walk indexes the record stream. The private
warehouse does not need the mod here (the game gives 1000: 240 + 760).

`CD 3732.DY` (`7903c206...`), installed by `MAJ-mod-diagnostic.bat`. Log:

### What the 24 info objects say (dumped once each, before the patch)

All 24 were already loaded at boot, so the lazy-pointer case did not arise. Word
at `+0x10` / word at `+0x14`, key = dword at `+8`:

| index (key = index+1) | base / max | |
|---|---|---|
| 7 (key 8) | **240 / 1000** | the private warehouse: `CAMP_KEY = 8` still holds, and the pair is at `+0x10/+0x14` |
| 14, 15, 16, 18, 21, 22, 23 | 10 / 1000 | **the 7 chests patched** |
| 17 | 10 / **1400** | the 8th object at 10, **skipped by the guard** (ceiling is not 1000) |
| 0-3 | 20 or 50 / 240 | |
| 4, 9, 11 | 300 / 300 | not extendable (the value twice, as on 3460) |
| 10, 19 | 50 / 50 | not extendable |
| 13 | 5 / 5 | not extendable |
| 5, 6, 20 | 1 / 12, 3, 36 | |
| 8, 12 | 240 / 240 | |

So the measured assumptions hold on 3732: capacity pair at `+0x10 / +0x14`,
`CAMP_KEY = 8`, key at `+8`. The old unguarded AX rule ("every object at 10")
would have raised **8**, as on 3460..3527; the guard raised 7.

### The one the guard skipped

Index 17 reads 10 / 1400. It is probably one of the 8 chest-like inventories
that earlier builds raised (five chests + three regional warehouses), whose
ceiling the game raised to 1400. If a chest still shows 10 in game, that is the
one, and the fix is to accept any ceiling of at least 1000 instead of exactly
1000 (`jne` -> `jb` on the `+0x14` compare in `apply_chest_guard`). Not done: the
user reports the chests fine, and the guard is the reason this build is safe.
