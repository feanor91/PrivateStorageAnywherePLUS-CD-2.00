# Port to Crimson Desert build 3460 (31 October 2026 update)

A second update one day after 3446, and the first in-game test of the vtable
hook written for 3446. Procedure in [PORTING.md](PORTING.md).

The installed build was `CD 3446.BB`, which the 3460 executable still loaded:
every runtime scan in it is shape-based, so the log is clean down to the last
four lines.

## The vtable hook talked itself out of it

```
  Vtable at base+0x59EB3A8, CanShow at base+0xA1D4640 (vtable offset 0xFFFFFFFFFFFFFBA0), active flag offset 0x130
CanShow:      OK base+0xA1D4640 (vtable)
...
  CanShow: slot unknown - trying the prologue hook
  FindPrologBoundary: unknown opcode 0x74 at pos 10
HOOK CanShow: prolog boundary not detected (got 0), falling back to fixed 14 bytes
HOOK CanShow: ABORT — hook-table full or hookSize 0 exceeds slot capacity
```

The slot *was* recorded; the guard rejected it. It required the slot to hold
the address the resolver reported, and it does not:

```
slot  game+0x59EAF48  ->  game+0xEE33D0:  e9 6b 12 2f 09   jmp game+0xA1D4640
```

A five-byte `jmp rel32` thunk. The resolver follows it (ASI `0x9679..0x9685`
chases both `E9` and `FF 25`) and reports, logs and stores the far end, so
comparing the slot against *that* can only fail. The hook declined, fell back
to the prologue it cannot steal, and aborted — the same silent panels as
before, by a different route.

**Fix:** record the slot's raw contents alongside its address and use that for
both the check and the detour's original.

| `.psdata` | holds |
|---|---|
| `+72` | the slot address (`rsi` at the resolver's hit path) |
| `+80` | the qword in it — CanShow, or a thunk to CanShow |

```
SLOT (replaces `mov [VT_PTR],rdi` at 0x9965)
    [VT_PTR]     = rdi          ; the store it stole
    [.psdata+72] = rsi
    [.psdata+80] = [rsi]
    jmp 0x996C

HOOK(rcx = CanShow) -> al
    slot = [.psdata+72] ; orig = [.psdata+80]
    if slot == 0 or orig == 0:  log "slot unknown";          prologue installer
    if [slot] != orig:          log "slot ... now holds ..."; prologue installer
    VirtualProtect(slot, 8, PAGE_READWRITE, &old)
    [0x40950] = orig            ; the detour's "call the original"
    [slot]    = &detour (0xC0B0)
    VirtualProtect(slot, 8, old, &old)
    log "HOOK CanShow: OK vtable slot base+0x%llX -> detour (orig base+0x%llX)"
    return 1
```

Calling the thunk and calling CanShow do the same thing, so handing the
detour whatever the slot held is both simpler and more faithful than handing
it an address the resolver derived. The check is now "has anyone else written
to this slot since we read it", which is the question actually worth asking.

The mismatch path logs the slot and its current contents instead of a bare
"unknown", so a future build that moves this around says so in one line.

### Confirmed in game

```
HOOK CanShow: OK vtable slot base+0x59EAF48 -> detour (orig base+0xEE33D0)
...
  Warehouse opened (mode=0x04 sub=0x11)
AUTO-CAPTURED warehouse controller: 0x4E699160C00 (panelId=0x0000)
  Warehouse opened (mode=0x04 sub=0x05)
  ...
  InitWarehousePanel done state: ... +0x130=1 ...
```

The slot and the thunk are exactly the two addresses derived statically. All
six panels open, bind their own inventory (`CampWareHouse`,
`Housing_GatheredMaterials`, `Housing_Dresser`, `Housing_Refrigerator`,
`Housing_Symbol`, `Housing_Collecting`), title correctly and close cleanly,
over eleven open/close cycles including hotkey-to-hotkey switches. The
concern about direct calls and derived classes was unfounded on this build:
one vtable slot is the whole of it.

## Still open: no capacity is written at all

What the game actually shows, measured in game:

| panel | shown | expected |
|---|---|---|
| F4 Private | **553/1000** | 1000 |
| F5 Gatherables | **193/10** | 1000 |
| F6 Dresser | **79/10** | 1000 |
| F7 Refrigerator | **102/10** | 1000 |
| F8 Symbol | **0/10** | 1000 |
| F9 Collecting | **257/1237** | 1000 |

So it is the five housing chests that are broken, not the private warehouse —
the opposite of what the log suggested. They are back to their native ten
slots, while still holding the items a previous session let in (193 items in a
ten-slot chest). F9's 1237 is unexplained and noted below.

Two log facts, and they point at one struct.

**The slot patcher returns ≤ 0.** Its line

```
InventoryInfo slot patch: 5 entries default 10 -> 1000
```

is on 2850 and 2976 at line 42 and is *absent* on 3460. The worker thread at
ASI `0x13E0` calls the wrapper every second and logs that line whenever the
return is positive (`test eax,eax ; jle`), independent of the verbose flag, so
its absence means the patcher never patched anything. The patcher is
`0x8720`, called at `0x4612F` **before** the walk and independent of it:

```
mgr = [[INVMGR_PTR]]                     ; else return -1
entries = [mgr+0x58] ; count = [mgr+8]   ; else return -1
if count-1 > 0xFFF: return -1
for idx in 0..count-1:
    e = [entries + idx*8]
    if e and word [e+0x48] == 10: word [e+0x48] = 1000 ; n++
return n
```

The chests *are* at ten, so an intact patcher would have found them. Either it
bailed on `[mgr+0x58]` / `[mgr+8]`, or `word [e+0x48]` is no longer the
capacity, in which case it looked at every entry and matched none.

**The walk ends in `[PRIV] no entry`**, eleven opens, eleven times, where
every build through 2976 logged `[PRIV] base=… max=1000 exp=… n=18` and then
`[PRIV] container total … -> 1000`:

```
     1  [INVMGR_PTR] == 0                   -> no entry
     2  mgr = [[INVMGR_PTR]] == 0           -> no entry
     3  dword [mgr+0x6C] == 0               -> no entry
     4  dword [mgr+0x68] == 0  (nbuckets)   -> no entry
     5  NameToKey false -- unreachable, apply_f4 forces al=1
key      = word [rsp+0x28]              <- apply_f4 writes CAMP_KEY = 8
buckets  = [mgr+0x78]
bucket   = buckets + (key % nbuckets) * 0x100
     6  [bucket] == 0                       -> no entry
     7  key not among [bucket+d*8+8]        -> no entry
     8  [bucket+d*8+0xC] >= [mgr+8]         -> no entry
     9  [mgr+0x58] == 0                     -> no entry
    10  [[mgr+0x58]+idx*8] == 0             -> no entry
    11  word [entry+0x48] == 0              -> no entry
    12  word [entry+0x48] > 0x7D0           -> no entry
```

**Twelve** tests, one message — the first pass numbered only the last seven and
missed `0x461A2`, `0x461AE`, `0x461B8`, `0x461C2` and `0x461FA`, which are the
ones that read the manager's own fields and so are the likeliest to have
broken. Two quite different diagnoses fit: `CAMP_KEY = 8` is a **frozen
assumption** (the value `NameToKey` returned on 2.00, see PORTING.md §6) and
the enum may have renumbered — stages 6-7 — or a struct offset has moved,
which the log hints at elsewhere on this build (`+0x170 … not a pointer
(1.13+ layout)`, `handler+0x1E0 … not a tab index`, and `[CAP] +0x2CD 255->4
+0x2CC=230 +0x2CA=201` where every earlier build read `255->0 … 0 … 0`) —
stages 3-4 and 8-12. Only an offset explains the slot patcher as well, so that
is the reading to beat.

Static derivation of the key got as far as the `InventoryInfoKey` name pool:

```
game+0x5C64760  PearlUser Money WareHouse CampWareHouse PetAndVehicle
                PearlCharacter Housing_Dresser Recovery BirdFeed CampStraw
                Housing_GatheredMaterials Housing_Collecting Housing_Symbol
                Housing_Refrigerator SpagnolaWareHouse XamacaWareHouse
                InvisibleInventory Kuku NoCheck ConvertMoney ConvertItem
                DragnarWareHouse
```

22 names, each referenced twice from a registration run at `game+0x1D99A6..
0x1DB86D` — but the immediates there are `std::string` lengths (`mov edx,0xE`
and `mov ecx,0xD` for the 13-char `CampWareHouse`), not keys, no pointer array
indexes the pool, and the map is built by obfuscated code. Neither the pool
order (CampWareHouse 4th) nor the registration order (5th) gives 8, so the key
is not an index into either. It cannot be derived this way.

So the next step is to make the log answer it instead — not just which test
refused, but what the struct now looks like, since that is what a fix needs:

```
  [PRIV] no entry: stage %u key %u ax %u
  [DBG] mgr+%02X = %016llX
  [DBG]   mgr+%02X deref +%02X = %016llX
  [DBG] slot patcher -> %d
```

667 bytes, in the 1984 bytes of unreferenced zero padding between AX's string
pool (ends `0x4683F`) and its next block (`0x47000`) — no branch and no
absolute pointer in the image lands there, and the section is RX, so nothing
could have been using it as a buffer. `.pstext`'s own tail had 42 bytes left,
which is why the padding was worth establishing.

- Each of the twelve `jcc`s keeps its opcode and length; only its rel32 moves,
  to a stub that sets a stage number in code order and joins a tail that keeps
  AX's verbose check. `key` and `ax` are meaningful from stage 6 on — before
  `0x46205` the key slot is uninitialised.
- The two stages where `rax` still holds the manager dump it on the way out,
  and so does the slot patcher's call site, which is wrapped so the dump runs
  first and the patcher's return value is logged — once per distinct value,
  since the worker calls it every second.
- The dump walks `mgr+0x00..0xF8` as qwords and, for any that the AZ block's
  `rdbl` helper says points at readable memory whose own first qword is also
  readable, prints sixteen qwords from there. One indirection past the manager
  is enough: a field holding the entry array shows the first entry's header,
  where a `10` is the capacity word the patcher is hunting for. Every deref is
  behind a `VirtualQuery`, so a wrong guess logs nothing instead of crashing.

### What the diagnostics answered: stage 12, and only stage 12

```
  [DBG] mgr+00 = 0000000145C64A58     <- the vtable, base+0x5C64A58, as line 31 says
  [DBG] mgr+08 = 0000056F00000018     <- dword [mgr+8]  = 24 entries (was 18)
  [DBG] mgr+58 = 000005700EFF09A8     <- the entry array
  [DBG] mgr+68 = 0000001800000001     <- [mgr+0x68] = 1 bucket, [mgr+0x6C] = 24
  [DBG] mgr+78 = 0000056FF831D700     <- the bucket array
  [DBG] slot patcher -> 0
  [PRIV] no entry: stage 12 key 8 ax 6144
```

Stage 12 is the last of the twelve, so every test before it passed. In order,
that clears the whole chain:

| assumption | verdict |
|---|---|
| `INVMGR_PTR`, the manager object | found (stages 1-2 passed) |
| `[mgr+0x6C]`, `[mgr+0x68]` (nbuckets = 1) | sound (3-4) |
| **`CAMP_KEY = 8`** | **still correct — stage 7 did not fire, so key 8 is in the bucket** |
| `[mgr+0x78]`, the bucket layout, the entry index | sound (6-8) |
| `[mgr+0x58]` entry array, `dword [mgr+8]` count | sound (9-10) |
| `word [entry+0x48]` as the base capacity | **wrong**: reads 6144, so stage 12 refuses it as over `0x7D0` |

One frozen assumption out of the whole table, and it is the one the slot
patcher also depends on: it compares `word [e+0x48]` against 10 across all 24
entries, found none, and returned 0. **One moved field explains both failures**,
and `CAMP_KEY` -- the assumption I expected to be the culprit -- is fine.

The manager also carries a 24-word permutation of 0..23 at `+0xA0..+0xCF`,
which agrees with the count: the game went from 18 inventory kinds to 24, and
the name pool at `game+0x5C64760` lists 22 of them.

Entry[0] of the array looks like this, and the only recognisable capacity in it
is at `+0x14`:

```
+00 = 00000570043D1040   +40 = 0000000100000001
+08 = 0001010100000001   +48 = 00000570043D05C0   <- a pointer now, not two words
+10 = 000000F0FFFF0014   +50 = 0000000100000280
      ^+10=20 ^+12=FFFF  +58 = 0000000000000028
      ^+14=240 (0xF0)    +60 = 00000570057A5340
+18 = 0000057004FE64E0   +68 = 00000570043D0C80
+20 = 0000000100000001   +70 = 0000000100000680
+28 = 0 / +30 = 0        +78 = 0000000000000028
```

240 is the private warehouse's historical base, so `+0x14` is the candidate --
but one entry cannot settle it, and guessing would mean writing 1000 into an
unknown field of a live save. So the second diagnostic build dumps all 24
entries, `[[mgr+0x58] + j*8] + k*8` for `k` in 0..13, three levels down. Five
of them hold 10 at whatever offset the capacity has moved to; that offset is
the fix.

### Also unexplained

F9 (Collecting) shows `257/1237` where its four siblings show `/10`. All five
housing panels are given the same `PanelValue` — `0x2D1`, the Gatherables
type-id from the INI — because `HGM string slot` and the type resolver are
both off on this build (`WARN string-xref scan failed`, `Type resolver:
DISABLED`), so the per-chest type-id lookup is unavailable. Whether 1237 is
Collecting's own number or a crossed binding is not yet known; the
`SetInventory` bind strings are correct per panel (`Housing_Collecting` etc.)
and the titles are right, so the cross, if any, is not in the binding.

both; the installed build says which.
